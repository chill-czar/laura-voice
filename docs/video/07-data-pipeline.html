Data Pipeline

How a sentence spoken out loud becomes a durable, queryable business record.

One utterance, end to end

01

Caller speaks

"I was rear-ended on the 26th of May in Mumbai, hurt my leg."

audio frames → Deepgram nova-3
02

STT emits finals — usually several

Streaming STT fragments one thought into multiple finals. This is why extraction uses a rolling window of the last 6 turns rather than one utterance.

user.transcript.final ×N
03

Transcript persisted immediately

CallOrchestrator.recordUserTurn() writes a TranscriptTurn row before anything else happens.

Postgres: TranscriptTurn(speaker=CALLER, text)
04

Structured extraction — background, non-blocking

A second LLM call with a strict JSON schema pulls typed facts out of the free text. It runs detached so it never delays the spoken reply.

{ "incidentType": "motor_vehicle_accident",
  "incidentDate": "2026-05-26",
  "incidentLocation": "Mumbai",
  "injuries": ["leg"] }
05

Validated before it is trusted

The model's JSON is re-parsed through intakeFieldsSchema.safeParse(). Invalid output throws and becomes an error event — it never reaches the database.

zod validation boundary
06

Merged into live state

CallState.mergeIntakeFields() — nulls and empty arrays are skipped, so a later turn can add facts but a blank extraction can't erase them.

returns updatedKeys[]
07

Persisted through a typed service

CaseService.updateIntake() is the only writer. Field names match IntakeFields 1:1 — no translation layer to drift.

Postgres: Matter row updated
08

Event emitted to three places

intake.fields_extracted → Postgres CallEvent + Redis stream + Redis pub/sub + console.

EventService.emit()
09

Frontend updates live

Redis pub/sub → API SSE → React. The Case Details panel fills in mid-sentence, with no polling.

useCallEventStream → deriveCallState
10

Next turn's context is different

missingRequiredFields shrinks, so the assembled prompt changes and the agent asks about something else.

the loop closes
Notice what never happens: the model never writes to the database. It produces a proposal, the proposal is validated, and a typed service performs the write. If the model hallucinates a field, validation rejects it — and I get an error event rather than silent corruption.

Schema — every call is fully reconstructable

  Caller ──1:N── Matter ──1:N── Appointment
  (phone @unique)  │              (idempotencyKey @unique)
        │          │
        └──1:N── Call ──┬──1:N── TranscriptTurn   (speaker, text, timestamp)
       (roomName @unique)└──1:N── CallEvent        (type, agent, phase, metadata, durationMs)

Matter — 13 structured intake fields

incidentType · incidentDate · incidentLocation · incidentDescription · injuries[] · treatmentReceived · emergencyServicesInvolved · policeReport · insuranceInformation · otherPartyInformation · witnesses · lostWages · representedByAttorney

Plus status, qualificationStatus, notes.

Why CallEvent is its own table

  • The call can be replayed from events alone — the frontend literally does this via deriveCallState()
  • durationMs on the row makes latency queryable in SQL
  • Indexed on callId and type — "show me every tool.failed this week" is one query
  • It's the audit trail a law firm's compliance person would actually want

CallState (memory)Current phase, collected fields, turn stateNoIn-flight call degrades; everything already persisted survives
Why persist per-turn instead of at call end? Because calls drop. If I only wrote on call.ended, a caller hanging up mid-intake would lose everything they just told us. Writing as facts arrive means a dropped call still leaves a partially-complete matter a human can pick up.

The claim I will not make

"AI output is the source of truth." It isn't, anywhere in this system. The LLM's free-text reply is conversation. The structured extraction is a proposal. Only after zod validation and a typed service call does anything become business state. Every write is attributable to a specific tool call, logged with its input, output and duration.

That distinction is what makes this deployable at a law firm rather than a chatbot demo.
