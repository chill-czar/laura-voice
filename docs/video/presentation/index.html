A working voice-AI intake system for a plaintiff law firm — realtime voice, multi-agent orchestration, deterministic business state, and a full audit trail.

Built after the interview, from the gap the interview identified.

01 · The challenge

"If you remove Vapi, can you build
what's underneath it?"

Honest answer at the time: I understood the voice stack through provider abstractions. I could ship with them. I hadn't gone deep enough into the orchestration and runtime layer they hide.

Rather than say "give me an assignment and I'll learn it", I took the gap and built the system without hiding behind the abstraction.
02 · What I learned

Voice AI is not audio → LLM → audio

transport→ media→ VAD→ endpointing→ STT→ orchestration→ context→ LLM→ tools→ state→ TTS→ observability
  • VAD ≠ endpointing. "Is there sound now" is easy. "Is this person finished" is the hard one.
  • Every boundary is somewhere to lose latency, information, or control.
  • The interesting engineering is between the models, not inside them.
03 · Architecture in one sentence
LiveKit owns realtime media and the voice pipeline. My orchestrator owns the business state machine. Agents are specialised reasoning policies. Tools are the only way the model mutates business state. Postgres is durable truth, Redis is ephemeral events, OpenRouter is model routing, and the frontend is a thin observability layer.

This sentence is still true of the code as written — that was the design constraint.

05 · Cascaded vs speech-to-speech

Cascaded — used here

audio → STT → text → LLM
     → text → TTS → audio
  • Exact transcript by construction
  • Debuggable at every boundary
  • Swap any of 3 models independently
  • Text in / text out ⇒ evals are scriptable

Speech-to-speech

audio → encoder → repr → model
     → repr → vocoder → audio
  • Keeps prosody + emotion
  • Lower latency floor
  • Harder to audit and debug
  • Whole-stack lock-in
For legal intake the transcript isn't a debugging convenience — it's part of the deliverable. That decided it.
06 · What's lost at the STT boundary

Text is a lossy representation of speech

Survives

  • Words
  • Rough timing

Lost

  • Prosody, intonation
  • Emotion / distress
  • Speaker identity
  • Background acoustics

Consequence

"Fine." said angrily and "Fine!" said with relief become identical text.

A deliberate tradeoff — not an oversight. I chose auditability over acoustic nuance, and I can say exactly what that cost.

07 · Orchestration

The LLM proposes. Code decides.

USER SPEECH
   ↓
 probabilistic   LLM ──── proposes: "move to qualification"
   ↓
 deterministic  CallOrchestrator.prepareHandoff()
   ↓            └─ isTransitionAllowed(INTAKE → QUALIFICATION)?
   ↓               no → return null — the tool is simply refused
   ↓
 validated     ToolRegistry.wrap() ── zod
   ↓
 durable       PostgreSQL

An LLM is probabilistic. A business process must be deterministic. That's why they're separate layers.

08 · State machine

9 phases, explicit legal edges

GREETING→ TRIAGE→ INTAKE→ QUALIFICATION→ SCHEDULING→ CONFIRMATION→ COMPLETED

↺ QUALIFICATION → INTAKE when the result is INSUFFICIENT  ·  HANDOFF_HUMAN · ERROR_RECOVERY

  • Transitions live in a data table, not if statements — printable, testable, showable to a customer
  • Adding a phase is a data change, not a refactor
  • The LLM cannot set the phase. It can only call a tool that requests one
09 · Agent routing & handoffs

Four agents, one shared state

Triage

Why are they calling? Route to intake, answer from policy, or escalate to a human.

Intake

Collect facts conversationally. 6 data tools. Never invents anything.

Qualification

Explains a decision it did not make. Has no tool that can change the outcome.

Scheduling

Mock availability + idempotent booking + confirmation.

Agents exist only where instructions, permitted tools, or reasoning behaviour genuinely differ — not one per operation.

10 · Deterministic qualification

The rule a law firm can read

export function evaluateQualification(input) {
  if (input.representedByAttorney === true)
    return { status: DISQUALIFIED, reasons: ["already_represented_by_attorney"] };

  if (hasInjury && supportedType && dateKnown)
    return { status: QUALIFIED, reasons: [] };

  return { status: INSUFFICIENT, reasons };
}

Zero LLM calls. Pure function. Same input, same answer, every time — versionable, auditable, unit-testable.

11 · Context engineering

What reaches the model — and what doesn't

Included, per turn

  • Role instructions (per agent)
  • Current phase
  • Known caller
  • Collected matter fields
  • Required missing fields
  • Topic-scoped policy only
  • Global hard rules

Deliberately excluded

  • Full transcript
  • The whole database
  • All policy documents
  • Empty / null fields
  • Raw tool JSON dumps
  • Tools this agent may not use
On a voice call the caller is listening to silence while the model reads context. Prompt size is a latency decision.
12 · Data pipeline

AI output is not the source of truth

caller speaks
  → transcript            persisted immediately
  → structured extraction strict JSON schema, background
  → zod validation        ← the trust boundary
  → CallState merge       in-memory
  → CaseService.update()  only writer
  → PostgreSQL            durable
  → CallEvent             PG + Redis + SSE + log
  → next turn's context differs
  • The model returns a proposal, never a database write
  • Persisted per turn — calls drop, and a dropped call should still leave a usable matter
13 · Latency

Measured per stage, not guessed

TTFT
llm.completed · metadata.ttftMs
TTFB
first_audio · durationMs
EOU
latency.end_of_utterance
  • Stream at every boundary — never wait for a complete artifact to start the next stage
  • TTS begins on the first sentence, so response length stops affecting perceived latency
  • Extraction moved off the critical path — inline, it cost two sequential LLM calls per turn
  • Honest gap: the aggregate turn metric is derived from timestamps, not emitted
14 · Interruption

Barge-in is a state machine, not a boolean

LISTENING→THINKING→ SPEAKING→ INTERRUPTED→ TOOL_EXECUTING→ENDED
  • Token stream aborted · queued TTS discarded
  • Audio already played can't be recalled → truncated message goes into context so the model knows what was actually heard
  • Tool calls run to completion — a half-done write is worse than a wasted one; idempotency makes retry safe
  • TurnState is separate from CallPhase — being interrupted doesn't change what stage of intake you're in
15 · A real bug worth showing

The agent was interrupting itself

04:10:41  first_audio             charactersCount=148 (320ms)
04:10:42  user.transcript.partial "So yeah."     ← every single time
  • Agent's own voice → speakers → mic → VAD scored it as the caller talking
  • Default minWords is 0: any ~500ms of speech-like audio cancels the agent
  • Fix: explicit echo cancellation on capture + minWords: 2
  • The event timeline was the diagnosis. That pattern is the bug — no guessing required
This is what the observability layer is for.

18 · Evaluation

How would I know it's actually good?

Current state: no automated evals exist. This is the biggest gap in the project, and here's exactly what belongs here.

Tier 1 — unit

  • Qualification rules
  • Phase transitions
  • Field merging
  • Tool input schemas

Tier 2 — integration

  • Caller + matter creation
  • Returning-caller retrieval
  • Double-booking → 1 row

Tier 3 — conversations

  • 20–30 scripted calls
  • Field recall / precision
  • Hallucinated fields = 0
  • Legal claims = 0
The failure mode isn't a crash — it's a confidently wrong record. The architecture is eval-ready; the evals aren't written yet.
19 · Forward-deployed fit

Messy workflow → running system

What a firm actually says

"Every time a new lead calls, someone asks the same questions, types it into a spreadsheet, checks whether we already know them, calls them back, and books a follow-up. And sometimes we lose the notes."

What I turned that into

  • 9 phases with legal transitions
  • 13 typed intake fields
  • 4 explicit qualification rules
  • 9 validated tools
  • A complete audit trail
The parts most likely to differ per customer — rules, policy docs, required fields — I deliberately made data, not code. When a firm tells me their real criteria, that's a config change on a call, not a prompt I have to re-tune.
