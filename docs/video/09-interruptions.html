Interruptions & Barge-in

The behaviour that separates "a voice interface" from "a phone call that feels human".

Why interruption = true is the wrong model

A boolean tells you an interruption happened. It doesn't tell you what to do about the four things already in flight: streamed tokens, queued TTS audio, audio already played into the caller's ear, and any tool call mid-execution. Those need different handling, so the system needs a turn state, not a flag.

LISTENING THINKING SPEAKING INTERRUPTED TOOL_EXECUTING ENDED
packages/shared/src/phases.ts → TurnState — deliberately separate from the business CallPhase
Two independent state machines. Being interrupted doesn't change what phase of intake you're in. Conflating "the caller is talking over me" with "we are in the qualification stage" would be a modelling error — so TurnState and CallPhase are separate types that evolve independently.

What actually happens, in order

t+0.0sAgent begins speaking → tts.started, then first_audio
t+0.4sAudio frames are already flowing into the LiveKit room — this audio cannot be recalled
t+1.2sCaller starts talking. VAD fires while session.agentState === "speaking" → interruption.detected
t+1.2sTurn state → INTERRUPTED, interruptionCount++
t+1.2sLiveKit cancels the in-flight generation: token stream aborted, queued TTS discarded
t+1.3sTruncated assistant message is committed to chat context — so the model knows it was cut off mid-sentence
t+1.9sNew user turn transcribed → user.transcript.final
t+2.6sFresh generation against updated context → llm.started → new reply
—If the "interruption" turned out to be noise, LiveKit emits a false-interruption event → logged as speech.cancelled

What happens to each in-flight thing

In flightOn interruptionWhy
LLM tokens still streamingGeneration abortedThe response was answering a question the caller has now changed
TTS audio queued but not sentDiscardedCheapest thing to cancel; biggest perceived win
Audio already playedCannot be undoneIt's in the caller's ear. This is why the truncated text is committed to context — the model must know what the caller actually heard
Conversation stateTruncated message recordedPrevents the agent repeating the full sentence as if nothing happened

That tool-call row is the interesting one. Cancelling a schedule_follow_up halfway through could leave an appointment row without the caller ever hearing confirmation. I'd rather complete the write and let the idempotency key (callId + appointmentRequestId) make a re-attempt harmless.

The code

session.on(AgentSessionEventTypes.UserStateChanged, (ev) => {
  // Barge-in heuristic: the user started talking *while the agent was speaking*.
  // That's an interruption, not just the next turn.
  if (ev.newState === "speaking" && session.agentState === "speaking") {
    orchestrator.state.turnState = TurnState.INTERRUPTED;
    orchestrator.state.interruptionCount += 1;
    void orchestrator.eventService.emit(INTERRUPTION_DETECTED, {
      agent: orchestrator.state.activeAgent,
      phase: orchestrator.state.currentPhase,
      metadata: { interruptionCount: orchestrator.state.interruptionCount },
    });
  }
});

Tuning — and a real bug I hit

The failure

Replies appeared in the transcript but produced no audio — roughly one second after the agent started speaking, every time.

The log showed the shape of it immediately:

04:10:41  first_audio            (320ms)
04:10:42  user.transcript.partial "So yeah."

The agent was interrupting itself: its own voice came out the speakers, the mic picked it up, VAD scored it as the caller talking, and the system cancelled its own speech.

The fix — both ends

  • Browser: explicit echoCancellation, noiseSuppression, autoGainControl on capture instead of a bare audio boolean.
  • Agent: turnHandling.interruption.minWords = 2. The default is 0 — meaning any ~500ms of speech-like audio cancels the agent. A cough, a chair creak, or its own echo.

Real barge-in still works — "Wait, Friday instead" is well over two words — but noise no longer kills a sentence.

This is a good story to tell because it shows the observability paying for itself. I didn't guess; the event timeline showed first_audio followed one second later by a user transcript, every single time. That pattern is the diagnosis. Without per-event timestamps I'd have been randomly changing settings.

Honest limitations

  • Detection is VAD + word-count, not semantic. A genuine backchannel ("mm-hmm", "right") of two or more words will still interrupt. Semantic turn detection would fix this properly.
  • LiveKit's resumeFalseInterruption requires an audio output that supports pause; if it isn't supported on this path it's silently ignored, so a false interruption ends the utterance rather than resuming it.
  • There is no automated test for interruption behaviour. It's verified by hand, on camera. That's honest, but it's not a regression guard.
