Context Engineering

Exactly what reaches the model on every turn — and, just as important, what doesn't.

The assembled prompt, block by block

roleInstructionsper-agent — differs for Triage / Intake / Qualification / Scheduling
CURRENT PHASEfrom state.currentPhase — the model always knows where it is
KNOWN CALLERname / phone / email, or "unknown (not yet collected)"
KNOWN MATTER FIELDSonly fields actually collected — empty ones are omitted entirely
REQUIRED MISSING FIELDSderived getter — this is what drives the next question
RELEVANT POLICYtopic-selected docs only, not the whole knowledge base
RECENT CONVERSATIONoptional bounded excerpt — caller passes it in explicitly
GLOBAL RULES7 hard constraints — no legal advice, no invented facts, one question at a time
apps/agent/src/orchestrator/ContextService.ts → buildInstructions()

What I deliberately leave out

✗ full transcriptgrows unbounded; LiveKit already maintains the chat context window
✗ whole databaseirrelevant callers/matters are noise that invites cross-contamination
✗ all policy documentsScheduling doesn't need escalation rules; Triage doesn't need appointment rules
✗ empty/null fields"incidentDate: null" teaches the model nothing but costs tokens
✗ raw tool JSON dumpstool results return typed summaries, not entire rows
✗ every tooleach agent only sees the tools its role permits — capability scoping
Context engineering isn't "write a good prompt". It's deciding, per turn, what subset of the world the model is allowed to see — and being able to reconstruct exactly that later when something goes wrong. One class owns that decision, so there's one place to audit.

The code

buildInstructions(params) {
  const sections = [
    roleInstructions.trim(),
    `CURRENT PHASE\n${state.currentPhase}`,
    `KNOWN CALLER\n${formatCaller(state)}`,
    `KNOWN MATTER FIELDS\n${formatFields(state)}`,
    `REQUIRED MISSING FIELDS\n${state.missingRequiredFields.join(", ") || "none"}`,
  ];
  if (policyTopics.length > 0)
    sections.push(`RELEVANT POLICY\n${this.policyService.getDocs(policyTopics)}`);
  if (recentTurnsExcerpt)
    sections.push(`RECENT CONVERSATION\n${recentTurnsExcerpt}`);
  sections.push(GLOBAL_RULES);
  return sections.join("\n\n");
}

Policy retrieval — topic selection, not similarity search

How it works

Six documents load once at boot (4 markdown + 2 JSON). Each agent declares which topics it needs:

Triage        → ["communication", "escalation"]
Intake        → ["intake", "communication"]
Qualification → ["communication"]
Scheduling    → ["appointment", "communication"]
services/PolicyService.ts

Why no vector DB

  • The corpus is six documents. Every query is an exact lookup by topic.
  • Embeddings would add an index, a similarity threshold, and a whole new failure mode — to solve retrieval I don't have.
  • Caller/matter retrieval is a primary-key lookup, not semantic search.
The honest version: "I'd add embeddings when the knowledge base is big enough that topic routing stops working — not before."

The feedback loop that makes this "engineering" not "prompting"

caller speaks
   → structured extraction (strict JSON schema + zod re-validation)
   → CallState.mergeIntakeFields()          // in-memory truth
   → CaseService.updateIntake()             // durable truth
   → missingRequiredFields recomputed       // derived getter
   → NEXT TURN'S CONTEXT IS DIFFERENT       // ← the loop
   → agent asks about something it still needs

The prompt is never static. Each turn it reflects everything known so far — which is why the agent stops asking about injuries once injuries are recorded, without any explicit "don't repeat yourself" instruction.

Token/latency argument, if pushed: every block I exclude is tokens I don't pay for and time the model doesn't spend reading. On a voice call the user is listening to silence while the model reads context — so prompt size is a latency decision, not just a cost one.
